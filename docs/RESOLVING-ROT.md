# Resolving rot (a patch no longer applies)

`apply-series.sh` fails closed: the pipeline keeps the last good release and
opens an issue. This is how to fix the series by hand. Budget: one patch, one
file, usually under an hour.

## 1. Reproduce and read the report

```
git fetch upstream master --tags
tools/apply-series.sh <upstream-tag-or-master> --report /tmp/rot-report.md
```

The output names the failing patch (`FAIL [group] <file>`), the conflicting
files and, in the report, the conflict hunks. Note the group: if only
`touch-menu` fails, you can ship posture-core immediately with
`--skip-group touch-menu` (remove the group from `groups_enabled` in
`policy.yml`) and fix the touch menu later. Never publish a series that applies
only partly by accident.

## 2. Resolve in a scratch worktree

```
git worktree add --detach ../rot-fix <upstream-tag>
cd ../rot-fix
git am --3way ../ml-automation/patches/0001-*.patch      # repeat in series order
# on conflict:
git status                       # unmerged paths
$EDITOR <file>                   # keep upstream's change AND the patch's intent
git add <file>
git am --continue
```

Rules of thumb:

* Keep the patch minimal and additive. If upstream moved or renamed the code the
  patch hooks into, re-hook at the new place; do not copy upstream code into the
  patch.
* Do not touch submodule gitlinks, `.github/`, version files or installers in a
  patch. CI and version changes are generated by the pipeline.
* New source files must stay listed in `app/app.pro` / `tests/tests.pro` in the
  same patch that adds them.
* Which patch hits which file: see the table in `docs/ROT-MATRIX-2026-11-22.md`.
  `SettingsView.qml` (0002/0005) and `session.cpp` (0003/0007) are the usual
  suspects.

## 3. Check the result against intent

Before regenerating patches, compare with a reference where one exists:

* Same-tree check (base unchanged):
  `tools/apply-series.sh ea12abb4 --verify feature/stream-posture-sync` must
  still pass after you edit only context lines. If you changed behaviour it
  fails on purpose; review the diff it prints.
* Merge check (new base):
  `git merge-tree --write-tree <new-base> origin/feature/stream-posture-sync`
  gives git's own merge of the fork branch; `git diff <that-tree> HEAD` in the
  worktree should show only your conflict resolutions.
* Build: push the result as a `build/<tag>-nN` branch (pipeline) or run the
  fork's Windows workflow. Apply-clean is not build-clean.

## 4. Regenerate the series

```
cd ../rot-fix
git format-patch --no-signature --zero-commit -o ../ml-automation/patches <upstream-tag>..HEAD
cd ../ml-automation
git diff --stat patches/          # only the patches you fixed should change
tools/series-sha.sh            # new patch_series_sha256 -> upstream.lock
tools/rot-matrix.sh 5 --floor v6.2.0-daily.201
```

`--no-signature --zero-commit` keeps patch files byte-stable, so re-exporting an
unchanged commit creates no diff. If you add or remove a patch, update
`patches/series` (keep the `# group:` markers) and fix the numbering. Never
pipe `git format-patch` or `git diff` output through PowerShell; use `-o` /
`--output=` (PowerShell re-encodes the text and corrupts patches).

## 5. Commit and unblock

Commit `patches/` and `upstream.lock` (new `tag`, `commit`,
`patch_series_sha256`) to the `automation` branch with a message that names the
upstream change that caused the rot (`git log <old-tag>..<new-tag> -- <file>`).
The next scheduled run picks it up. Close the pipeline's rot issue.

## When not to fix the patch

* Upstream implemented the same thing: drop the patch and note it in the series.
* The conflict is in a file the patch only touched for convenience (for example
  a source list): reorder or split so the hunk is smaller.
* The hunk is security or installer related: stop and have it reviewed
  (PLAN R-SEC-5).
